# Design

## Context

What the change builds on:
- **A vote's page** (`app/src/routes/votes/[id]/`) is written at build time from
  `app/static/data/votes.json` and the vote's file `app/static/data/votes/<id>.json`; the browser
  loads no file of entries (spec `verdicts`).
- **The pipeline** (`pipeline/`, Python with polars, run by uv) reads the BFS vote-day files,
  the Federal Chancellery and the BFS register of municipalities, checks them, and writes the
  data files only when every check passes (`update.py`). The list of municipalities is the
  register's on the reference date that the vote-day files state, 2026-01-01.
- **Nothing draws a map yet**, and no data file holds geometry.

`investigations/map-data.md` holds the facts found while proposing:
- **The register gives boundaries.** Its K4 boundaries of a date are exactly the municipalities
  of its list on that date (2,110 on 2026-01-01), as a shapefile in LV95. It has no lakes, and
  it refuses dates in the future.
- **ThemaKart has the lakes.** The BFS ThemaKart set 2026 has the same 2,110 municipalities, but
  simplified differently: for 90% of them the corner farthest from the other version lies
  within 785 m, at worst 2.9 km. It also has 37 lakes, whole, reaching up to 28.9 km past the
  border.
- **The lakes are holes.** In both sources the municipalities, the cantons and the country leave
  the lakes out.
- **Size:** the map as SVG paths, to the metre, is 367 KB, 163 KB gzipped.
- **Colours:** the distances of the colours are measured in `check_colours.py`.

A prototype, not kept, measured the drawing of the 2,110 municipalities as SVG in Chromium. Its
main-thread work per frame:

| Action | Normal CPU | CPU slowed 4× |
|---|---|---|
| Zoom step (change of the view box) | 0.7 ms median, 2.6 ms max | 3.9 ms median, 8.4 ms max |
| Recolour all 2,110 municipalities (#8's case) | 5.2 ms | 38 ms |

## Goals / Non-Goals

**Goals:**
- **One data file for the map**, written and checked by the pipeline. It is the same for every
  vote, and the browser loads it once.
- **Plain TypeScript for the logic**, with unit tests: the colour classes, the details of a
  municipality and the view's arithmetic. The Svelte component only lays them out, as in #4.
- **No new dependency of the app**, and nothing requested from another server.

**Non-Goals:**
- Simplifying, projecting or clipping geometry. The BFS's shapes are used as delivered, rounded
  to the metre.
- Touch gestures and a layout for small screens (#10).
- Recolouring while the visitor interacts (#8). This change colours once per page.

## Decisions

Decisions 1 to 12 were asked while drafting, on 2026-11-15, in three rounds of questions; each
records the answer and the alternatives. Decision 1 was asked twice: the first answer rested on
my wrong statement that both sources have the same geometry. Decisions 13 to 20 follow from
them and were not asked one by one.

### 1. The register's boundaries, with ThemaKart's lakes

The municipalities, the cantons and the outline of Switzerland come from the BFS register of
municipalities, for the list's reference date. The lakes come from the BFS ThemaKart set 2026.
- **Why the register:** it is the source of the list, so the boundaries fit the list by
  construction, and they exist for any date up to today.
- **Why ThemaKart for the lakes:** no other BFS source has them.

The two sources are two simplifications (Context). They meet only at the lake shores, which
decision 13 covers.

Alternatives considered:
- **ThemaKart for everything.** One matched set of layers. Rejected: a year's set appears only
  in February (2 Feb 2026, 14 Feb 2025). An update after the vote-day files switch to a new
  year's list would stop until then; in 2025 the first vote day was 9 Feb.
- **The register alone**, with the lakes as the holes of the municipalities. Rejected: the
  border lakes (Lac Léman, Bodensee) are not holes but outside the country's outline. They would
  be missing.
- **swisstopo's swissBOUNDARIES3D** (1:25,000). Rejected: about 100 times the points. It would
  have to be simplified, which changes the geometry, and it has no lakes either.
- **A ready-made TopoJSON from npm** (for example the package `swiss-maps`). Rejected: derived
  by a third party and not regenerated by our pipeline (hard constraint 4), and an app
  dependency.

### 2. The level K4

The BFS's coarsest simplification, made for maps from 1:500,000 to 1:5 million: 28,487 corners
for the municipalities, 163 KB gzipped for the whole map.

Alternatives considered:
- **G1** (1:300,000 to 1:600,000). Rejected: about three times the points and 2.5 times the
  size, for detail visible only far zoomed in. It also holds three areas that belong to no
  municipality, and its lakes would still be K4.

### 3. How the map follows the mergers

The pipeline asks the register for the boundaries of the list's reference date. A new list
(2027-01-01) brings its own boundaries in the same run, and the update stops when they do not
fit the list exactly.

The lakes are valid for all years, so the set of 2026 is pinned by its address (asset
36390072). A new set is taken by hand, by changing that address, when the BFS removes the old
one or its lakes change.

Alternatives considered:
- **Looking up the newest set by its order number** (`mb-x-00.07.01.01-<yy>`) on each run.
  Rejected: one more request and a search, for lakes that do not change.

### 4. SVG, with our own code to zoom and move

Each municipality is one SVG path, drawn by the Svelte component:
- **Zoom and move** change the SVG's view box; the browser redraws.
- **Pointing:** the browser itself finds the municipality under the pointer, through pointer
  events on the paths.
- **Inputs:** the mouse wheel, the buttons "+", "−" and "Ganze Schweiz", and dragging with
  Pointer Events. No pinch: that is #10's.

Q added a condition: before v1 ends, check whether a library would serve better. #10, which
needs pinch, takes this up as an open decision in `docs/roadmap.md`.

Alternatives considered:
- **SVG with d3-zoom.** Pinch included, about 10 KB gzipped, six small packages. Kept for the
  check in #10.
- **Canvas.** Faster to recolour (#8), but our own hit-testing to find the municipality under
  the pointer, and a redraw on every zoom step. Rejected for now.
- **MapLibre GL.** WebGL, smooth, about 250 KB gzipped. Rejected: much for a map without a
  background map.

### 5. Blue-green for yes, orange-red for no

From class 1 to class 4:
- **No:** `#fbbea3`, `#e5946f`, `#c2673b`, `#934319`.
- **Yes:** `#92dfd0`, `#4bc1ad`, `#009c86`, `#007260`.

In OKLab, each side has one hue (about 45° and 180°), and lightness falls by the same steps on
both sides. With red-green colour vision deficiency, the same class of yes and of no differs by
Delta E 9.3 to 10.4, and the palest class by 6.9 (`investigations/map-data.md`, 6). That palest
pair is legal only with a second cue: the details a visitor gets by pointing, and the legend.

Alternatives considered:
- **Classic green and red** (ColorBrewer's Reds and Greens). Rejected: Delta E 3.5 to 8.1 with
  red-green deficiency.
- **Green and purple.** About as safe, but no is not red.
- **Blue and orange.** The safest (7.5 to 20), but gives up green for yes.

Q's question showed an earlier candidate's figures (4.4 for the palest pair, 0.6 to 5.8 for a
classic pair). The tuned colours above and ColorBrewer's are the measured ones. The choice
stands.

### 6. Four classes of ten points per side

A class is that of the side with more votes: 50 to 60%, 60 to 70%, 70 to 80%, 80% or more.
- **Why ten-point classes:** the municipal shares spread widely. Over all votes, 23% of
  municipal results are below 30% yes and 11% at 70% or more.
- **Exact comparison:** the class is compared in whole numbers, `10 · winner ≥ 6 · (yes + no)`
  and so on, so that a share of exactly 60% is class 2 without floating-point doubt.
- **Ties:** a municipality with as many yes as no votes (765 of 263,005 municipal results) takes
  the neutral `#f0efec`.

Alternatives considered:
- **Five classes of five points per side**, finer for close votes. Rejected: a third of all
  results fall into the two outermost classes.
- **A continuous scale.** Rejected: a share is hard to read off a colour without classes.

### 7. The figures in the page, the shapes and names loaded once

The page is written with each municipality's yes and no votes, about 30 KB. The browser loads
the shapes (`data/map.json`) and the names (`data/municipalities.json`) through a promise kept
in a module, so going to another vote's page does not load them again. The page still loads no
file of entries.

Alternatives considered:
- **The browser loads the vote's file of entries.** #8 needs the entries in the browser, but
  this reverses "The page holds its result" now. Rejected; #8 decides.
- **The map inside every page.** It would show without JavaScript. Rejected: about 400 KB more
  per page, and nothing cached between pages.

### 8. A municipality without a result is hatched

Grey diagonal lines on white, with its own entry in the legend. Pointing at it says why it has
no colour.

Alternatives considered:
- **The colour of the neighbour that counts its votes.** Rejected: the data does not record the
  neighbour. ThemaKart's "Gemeinden (Politik)" has the pairing only for 2025 and 2026.
- **Plain white.** Rejected: it reads as missing data.

### 9. No map for a tie-break question

Its "yes" means "for the initiative", and the calculation does not judge it.

Alternatives considered:
- **A map of the share for the initiative**, with a legend of its own. Rejected: a second
  meaning of the same colours.

### 10. A budget of 16 ms per frame, checked by a browser test

A zoom step, a move or pointing at a municipality takes at most 16 ms of main-thread work per
frame, one frame at 60 Hz. The prototype measured at most 2.6 ms at normal CPU, a margin of
about 6.

How the test measures, without any test code in the app:
1. A script added before the page loads registers, on `window`, a listener in the capture phase
   for `wheel`, `pointermove`, `pointerover` and `click`. It notes the time, then asks for an
   animation frame before the app can.
2. A listener in the bubble phase notes when the app's handlers are done.
3. In that animation frame, which runs before the app's own, it notes the time again, then
   schedules a task, which runs after the browser has drawn the frame.

The work of the frame is the handlers' time plus the time from that animation frame to the
task. The test fails above 16 ms and prints every frame's figure.

Alternatives considered:
- **The same test with the CPU slowed 4×.** Rejected: a margin of only about 2 on a different CI
  runner.
- **Measured once by hand.** Rejected: a later change could break the budget unnoticed.

### 11. pyshp reads the shapefiles

The register's shapefiles (LV95) and ThemaKart's are read with pyshp: pure Python, MIT, no
dependencies of its own, and typed since version 3. It is pinned in `uv.lock` with the extra
`stubs` that marks it as typed for mypy strict.

Taking the register's shapefile rather than its GeoJSON avoids projecting from WGS84 to LV95.

Alternatives considered:
- **Our own reader** of about 30 lines with `struct`. Rejected: our own code and tests for a
  binary format, against one small, widely used package.

### 12. What pointing shows

A municipality's details:
- its name, with its canton's abbreviation in brackets unless the name already ends with it
  ("Benken (ZH)");
- its yes share, its yes votes and its no votes.

They appear in a box at the top left of the map, not at the pointer, so that nothing moves with
the mouse. A mouse shows them on hover; a click or a tap shows the same. Pointing at a lake or
outside Switzerland clears the box.

Alternatives considered:
- **Also the turnout.** Rejected: the page would hold twice the figures.
- **Name and share only.** Rejected: a municipality's number of votes would stay hidden.

### 13. Whole lakes, on a lake-coloured outline of Switzerland

The lakes are drawn as the BFS delivers them, including their parts outside Switzerland, as in
the BFS's own maps.

Under the municipalities the map draws the outer rings of Switzerland's outline in the lake
colour `#9fb8e8`. Every hole of the municipalities then shows as water:
- the lakes;
- lakes below 195 ha that ThemaKart does not have;
- the slivers where the register's shore and ThemaKart's lake do not meet.

Drawn without that layer, a prototype at 50 m per pixel left 11.0 km² uncovered. With
ThemaKart's own municipalities it left 9.8 km².

Alternatives considered:
- **Lakes cut at the border** with an SVG clip path. Asked, and rejected by Q.
- **No outline layer.** Rejected: white slivers along the shores when zoomed in.

### 14. The shape of `map.json`

```json
{
  "referenceDate": "2026-01-01",
  "lakesSet": 2026,
  "width": 348834, "height": 220583,
  "municipalities": [[1, "M3627 52304l1094 -486..."], ...],
  "cantons": [["ZH", "M..."], ...],
  "outline": "M...",
  "lakes": ["M...", ...]
}
```

- **Coordinates:** each is in whole metres from the top left of the smallest rectangle around
  Switzerland: `x − x_min` and `y_max − y`. They are written as SVG path data, a first point
  then relative steps, which SVG and the canvas' `Path2D` both read.
- **Order:** municipalities by number, cantons in the order of the constitution, lakes as the
  set lists them. That fixed order keeps the file the same, byte for byte, for unchanged sources
  (spec `vote-data`).
- **Not in the file:** the names, which are in `municipalities.json`, and the lakes' names,
  which nothing shows.

Alternatives considered:
- **Arrays of coordinate pairs.** Neutral, but about twice the size, and the app would build
  the paths itself.
- **TopoJSON.** Each shared border once, smaller. But it needs a library or our own decoding,
  and we change no geometry, so there is nothing to keep consistent.

### 15. The modules of the app

- **`app/src/lib/result-map.ts`:**
  - the class and colour of a municipality from its counts;
  - its details (decision 12);
  - the legend;
  - the figures of each municipality from the vote's file, checked against the map (spec "The
    figures fit the map").
- **`app/src/lib/map-view.ts`:** the view box of a zoom around a point, of a move, and their
  limits: 1× to 16×, centre inside the rectangle.
- **`app/src/lib/map-data.ts`:** loads `map.json` and `municipalities.json` once, with the site's
  path, and turns a failure into the message of the spec.
- **`app/src/routes/votes/[id]/ResultMap.svelte`:** the map, the buttons, the legend, the box of
  details, the source and the sentence on the Swiss abroad.

`+page.server.ts` reads `map.json` at build time only to check the figures against it. The
shapes do not go into the page.

### 16. Borders keep their width

The strokes have `vector-effect: non-scaling-stroke`: a border stays one width on the screen at
every zoom.
- **Municipalities:** white, 0.5 px.
- **Cantons:** `#333`, 1.5 px, drawn above the municipalities and the lakes.

The cantons' paths take no pointer events, so pointing reaches the municipality beneath.

### 17. A drag is not a click

A press followed by more than 4 px of movement is a drag. Its release does not select the
municipality beneath. A shorter one is a click.

### 18. The Swiss abroad and the source come from the data

- **The Swiss abroad:** their number of entries is counted when the site is built, from the
  vote's file and `municipalities.json` (`swissAbroad`): 12 in vote 5960, 11 in 5670.
- **The source line:** it takes the reference date and the lakes' set from `map.json`.

### 19. The texts

Every new text is in `app/src/lib/texts.ts`, in German until #9: the heading, the legend, the
buttons and their labels ("Vergrössern", "Verkleinern"), the details, the source, the Swiss
abroad, and the failure.

### 20. Accessibility within this change

- **The map** is an image to assistive technology: `role="img"` with a label naming the vote and
  that the table of the cantons gives the figures as text.
- **The buttons** are buttons, usable by keyboard.
- **The box of details** is a polite live region.

Reading a municipality's details without a pointer is #10's.

### Tests

- **Pipeline (pytest):** `tests/made_up.py` gains shapefile zips written with pyshp's writer. One
  test per check of the spec, each seen to fail first:
  - a municipality without a boundary;
  - a boundary of no municipality;
  - a number given twice;
  - a canton missing;
  - a set without lakes.

  Further tests:
  - the boundaries are asked for the list's date;
  - rounding to the metre;
  - the record of the sources;
  - the same bytes on a second run.
- **App (Vitest):**
  - `result-map.ts` with the figures of `investigations/map-data.md`, including the class
    boundaries 60% and 80%, the tie, the name that holds its canton, and a municipality without
    a result;
  - `map-view.ts`: zoom around a point, the limits, a move and its clamp;
  - the check of the figures against the map with made-up data;
  - the real data files: the map's municipalities equal the list, and every judged vote fits
    the map.
- **Browser (Playwright):** one test per scenario of `result-map`, among them:
  - the map's place and size;
  - the colours of named municipalities;
  - the hatching;
  - the legend;
  - pointing, clicking and the lake;
  - the zoom buttons and their limits;
  - the wheel;
  - dragging and its clamp;
  - the source and the Swiss abroad;
  - one load across navigation;
  - the blocked file;
  - the tie-break page;
  - the budget.

  The existing test that no page requests another server covers the map's loading.

### Dependencies added

- **pyshp 3.1.6**, with its extra `stubs`, in the pipeline (decision 11). Published 2026-07-25,
  older than two weeks. Its MIT licence and typing are checked when it is added.
- **Nothing in the app**, and no service at run time. The map's files are served with the site.

### Performance budget

- **Interactions:** 16 ms of main-thread work per frame for a zoom step, a move or pointing
  (decision 10).
- **Loading:** `map.json` is about 370 KB, 165 KB gzipped (GitHub Pages compresses JSON). It
  loads once per visit (decision 7).
- **Drawing:** the first drawing of the map is neither bounded nor measured by the tests; the
  budget covers the interactions. On the prototype, colouring all municipalities once took
  5.2 ms.
- **The pipeline:** a run downloads about 13 MB more and spends a few seconds more on reading.

## Risks / Trade-offs

- **[The register's boundaries are an address behind a web page, without documentation or
  terms]** → Its answer is checked like every source, and a change of address or shape stops
  the update naming the address. The source is named on the map.
- **[The terms differ]** ThemaKart's asset says OPEN-BY, while the PDF in the set still says the
  geometry may not be changed. → We follow the asset's terms, change no geometry beyond rounding
  to the metre and moving the origin, and show "Kartengrundlage: © BFS" with the dates, which
  meets both texts.
- **[The pinned ThemaKart set is removed]** → The update stops naming its address. The next
  set's address is found by its order number.
- **[Two simplifications meet at the shores]** → The outline layer fills every gap (decision 13).
  Where a lake overlaps a shore, it covers a sliver of land, visible only zoomed far in.
- **[K4 looks coarse at 16×]** → Accepted. G1 can follow if visitors zoom that far.
- **[Over the map, the wheel zooms instead of scrolling the page]** → The map takes part of the
  page's height, and the page scrolls with the wheel outside it. #10 decides the layout.
- **[The palest classes are close for colour-blind viewers]** (Delta E 6.9) → The figures on
  pointing and the legend are the second cue.
- **[A timing test on shared CI runners]** → A margin of about 6. A failure prints every frame's
  figure, to tell a slow runner from a regression.
- **[Each vote page grows by about 30 KB, and its `__data.json` as well]** → About 7.5 MB more
  for the site, of GitHub Pages' 1 GB.
- **[Recolouring is slow on a slow phone]** (38 ms with the CPU slowed 4×) → Not this change's
  concern. #8 sets its budget, and decision 4's check of a library or of canvas comes before
  v1.

## Migration Plan

1. While applying, run the update command for real. Review the diff: the new `map.json`, about
   370 KB, and `sources.json` with four more sources: the register's three answers and the
   ThemaKart set.
2. Merge by rebasing. CI publishes the site with the map.
3. Check by hand, on a computer and on a phone: `/votes/5960/` and `/votes/6650/` show the map;
   pointing works; zoom and move work.
4. Rollback: revert the commit on `main`. The map and its data file go, and the rest of the site
   is as before.

## Open Questions

- **The terms of use of the register's boundaries:** the pages state none. Naming the source on
  the map meets the BFS's terms elsewhere. A clarification would change nothing in this change.
